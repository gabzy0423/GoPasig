# ADR-001: Decoupling Route Geometry from Stops Lifecycle

## Status
Accepted

## Context
In the initial architecture of the GoPasig system, Route polylines and Stop configurations were tightly coupled. Whenever a stop was added, reordered, or deleted, the system queried all stops on the route and completely overwrote the route's `polyline_coordinates` JSON column with a simple point-to-point sequence of coordinates.

This design presented several major limitations:
1. **No Support for Winding Road Geometries**: It was impossible to define realistic, curvy route geometries that follow streets, as the polyline was always reduced to straight segments connecting stop coordinates.
2. **Duplicated Mathematical Calculations**: The Haversine distance formula was copy-pasted across multiple classes (`GPSKalmanFilter`, `Stop`, `ValidationService`, `GeofenceDetector`).
3. **Lack of Type Safety**: Latitudes and longitudes were passed as raw float pairs, increasing susceptibility to parameter ordering bugs and lack of structured telemetry metadata (like speed, accuracy, and bearing).

## Decision
To address these limitations, we refactored the geospatial architecture of the Routes module with the following changes:
1. **Decouple Polyline Overwrites**: We removed the automatic polyline regeneration hooks from the `StopController` CRUD methods. Now, Route geometries are preserved independently in the database.
2. **Type-Safe Value Objects**: We introduced the `Coordinate` and `Polyline` Value Objects to handle geographic positions and coordinate paths safely.
3. **Geospatial & Filtering Isolation**: We separated geographical calculation functions (`GeospatialService` for distances, bearings, bounds) from position estimation logic (`KalmanFilterService`), adhering to the Single Responsibility Principle (SRP).
4. **Route Geometry Repository**: We introduced `RouteGeometryRepository` (with key-based caching) to decouple controllers and views from direct Eloquent model geometry reads.
5. **Strategy Pattern for Routing Engine**: We introduced `RoutingProviderInterface` and `RoutingProviderFactory` to support switching between Manual (straight-line fallback), Google Directions, and OSRM providers via simple configuration changes.

## Consequences
- **GIS Preparedness**: The platform is now fully prepared to support winding road routing, Google Directions pathing, and snapped coordinates in future phases without modifying any database schemas or user workflows.
- **Unified Math Layer**: Duplicated geodesic distance logic has been consolidated under `GeospatialService`, simplifying future maintenance.
- **Cache Efficiency**: Route polyline queries are cached using `route_geometry_{$id}` and automatically invalidated when routes are updated.
